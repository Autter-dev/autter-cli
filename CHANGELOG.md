# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

This changelog is automatically generated by AI when releases are published.

## [Unreleased]

### Fixed

- **A note with its integrity stamp removed no longer passes as `legacy`.** Deleting the `integrity` member from a note and editing it made `autter verify` report `legacy` (exit 0, also with `--strict`), and `autter stats` then used the edited note: a commit with 83% AI lines could be reported at 33%. An unstamped note now passes as `legacy` only when it can have been written before stamping. A note whose metadata says autter 3.8.0 or later wrote it fails with the new status `stamp_removed` (exit 5, with and without `--strict`), since those releases stamp every note; so does a note with no autter version on a commit that descends from a commit whose note is stamped. `autter stats`, `autter blame` and range stats count its lines as unknown and print the one-line notice, and a rebase, amend, cherry-pick or `autter ci` merge that carries it writes `carried_failure`.
  - A note that says an autter older than 3.8.0 wrote it, on a commit after stamping began, is the new warning `unstamped_by_older_autter`: a teammate who has not upgraded writes exactly that, so it passes and its lines count, but `--strict` fails it (exit 5), as it fails `rebound_by_older_autter`, because the version cannot be checked. A repository whose notes all predate 3.8.0 still verifies as `legacy`, and so does an old note copied in by `autter notes backfill`.
  - "After stamping began" is commit ancestry, not dates, which can be set to anything and change on a rebase. autter computes the earliest stamped commits once and keeps them in `.git/ai/stamp_floor.json`, keyed by the notes ref, reading only the notes that changed when it moves; the check runs only for notes without a stamp.
  - Stash notes: an unstamped stash note that says autter 3.8.2 or later wrote it is no longer restored (until now it restored like one from 3.8.1), nor is one with no version made on a commit after stamping began.
  - Still not caught: a note whose stamp was removed and whose version was edited to a release before 3.8.0 (a warning after stamping began, `legacy` before it, and a failure only with `--strict`; a stash note edited to 3.8.1 or earlier still restores), and with the `http` notes backend only the version is checked.

## [3.9.1] - 2026-11-13

### Fixed

- **A cherry-pick keeps its AI attribution when git does not label it as one.** When a single commit was cherry-picked by a tool or hook that sets its own `GIT_REFLOG_ACTION`, the reflog entry did not say "cherry-pick", so autter could not tell which commit had been picked and the new commit's AI lines came out as untracked. autter now matches the picked commit by its content (the same patch) when the commit is the first parent of the new one, and only for an entry written by a cherry-pick or an amend, so an unrelated commit with the same changes is never taken for it.
- **Repositories whose path ends in a space work.** autter trimmed every space from the paths `git rev-parse` returns, so a repository in a folder such as `project ` was not found. Only the line ending is removed now.

## [3.9.0] - 2026-11-13

### Added

- **`autter verify` checks notes against the server's record in connected mode.** Until now, someone who could write the repository could edit a note and recompute its digest, and `autter verify` still said `verified`. The server now keeps every version of each note it receives, append-only, and `autter verify` compares each note with that record. A note that differs from the first version recorded, or whose record has more than one version, fails with the new status `changed_after_recorded` (exit 5), also when the author made the edit; the report says when the first version was recorded, by whom, and how many versions there are. A note the server has no record of yet is `not_recorded`, a warning (notes upload in the background), also with `--strict`. A commit whose note is missing here but recorded on the server stays `missing`, and the report says the server has one. With the `http` notes backend the only check is whether the record has more than one version.
  - When the record cannot be checked (local-only mode, not logged in, the server unreachable or older than the record), `autter verify` passes or fails on the local check alone and reports why in `record_check` (`--json`); it prints one line on stderr only in connected mode or with `--require-record`, not on every local-only run. `--require-record` fails both gaps with exit 5: a `not_recorded` note and a run whose record could not be read. `--no-record` skips the server.
  - autter no longer writes a second, different note for a commit whose note may already be on the server, so none of these reads as `changed_after_recorded`: a commit that keeps its SHA (a no-op rebase, picks that fast-forward, an amend that changes nothing, post-commit processing running twice) keeps the note it has, and an `autter ci` re-run that computes a different note for a merge commit already noted keeps the first one. The same note is not written or uploaded again. A note still queued and never sent can be replaced before it uploads: a cherry-pick stopped on a conflict and finished with a plain `git commit` uploads only its final note, not the provisional one written first. A note from before 3.8.0 on such a commit stays as it is instead of being stamped again. Notes are now written in a fixed order (files by path, entries by first line), so the same note computed twice, such as by a CI re-run in a fresh clone, is byte for byte the same; notes already written keep their text and still verify. `autter squash-authorship` still replaces a note the server has, since rewriting that commit's attribution is what it is for; the record then shows a second version.
  - `--json` adds `record_check` to the report and `record`, `local_status` and `record_summary` to results; no field was renamed.
  - Still not caught: anything in local-only mode beyond the integrity check, a note that was never uploaded, an edit made before the first upload the server saw (or before the server's upgrade, for a record marked `seeded`), and changes to the server's record itself.

## [3.8.4] - 2026-11-13

### Fixed

- **Commits no longer lose their authorship note when the background service is busy.** Every `git commit` starts a `git maintenance` process, which reports to the service on a connection of its own. If the service finished reading that process before it read anything from the commit, it took the commit's git process for dead and recorded the commit as finished without the new commit, so no authorship note was written while the commit was still reported as done. Only the command's own process now decides when it has finished; a git process that dies without reporting is still handled as before.

## [3.8.3] - 2026-11-13

### Fixed

- **`git stash pop`, `drop` and `stash branch` act on the right stash's attribution.** With the background service running and more than one stash on the stack, autter could record a `pop`, `drop` or `branch` against a different stash: it looked the stash up while git was already removing it. Popping the top stash then restored the attribution of the stash below it, and `pop stash@{1}` restored the top one's. Since 3.8.2 checks each stash note against its stash, the usual result was instead that the AI lines came back as untracked. autter now works out which stash was removed by comparing the stack git left with the stack before the command, and restores nothing rather than guess when they do not fit. `apply` was not affected.
- **`git stash branch` restores AI attribution onto the branch it creates.** It restored onto the commit the command started from, but `stash branch` first checks out the stash's base commit, so when those differed the AI lines were lost.

## [3.8.2] - 2026-11-13

### Fixed

- **A tampered stash note no longer comes back as AI attribution.** The note autter keeps for a stash (`refs/notes/ai-stash`) had no integrity stamp, so an edited one was restored on `git stash pop` and the next commit stamped it as a note that verifies. Stash notes are now stamped for their stash (its tree and the content of each attributed file, plus a digest) and checked on `pop`, `apply` and `stash branch`. A note that fails is not restored: its lines count as untracked, and one line on stderr says why (in daemon mode it goes to the daemon log). Stashes made with 3.8.1 or earlier have no stamp and restore as before.
- **`autter notes backfill` no longer re-stamps the notes it copies.** Notes copied from the local notes database into `refs/notes/ai` were stamped again on the way, so a note altered in the database came out `verified`, and a note from before 3.8.0 came out `verified` instead of `legacy`. Notes are now written exactly as stored: a good note still verifies, a failing one still fails `autter verify`, and an old one stays `legacy`. The command lists any failing notes it wrote.
- **`autter verify --strict` fails on `rebound_by_older_autter`** (exit 5). A note moved by an autter older than 3.8.0 cannot be checked against its digest, so a crafted one could turn any failure into a warning. Without `--strict` it is still a warning. `verify` now also checks what such a note's stamp says about the commit it names (its tree and file contents) when that commit is in the clone, and reports `content_mismatch` when a claim is false, or `carried_failure` when that commit's own note fails.
- Still not caught: a note or stash note edited with its digest recomputed (this needs the planned server-side record); a crafted rebound note whose claims hold or whose named commit is missing (a warning without `--strict`, and a rebase by this release stamps it again); a stash note with its stamp removed (restores like one from 3.8.1); direct edits to the working log in `.git/ai/`.

## [3.8.1] - 2026-11-12

### Fixed

- **A rewrite no longer turns a note that fails `autter verify` into one that passes.** In 3.8.0, when autter rewrote notes during a rebase (including reorder, squash, fixup and renames), an amend, a cherry-pick, or an `autter ci` squash or rebase merge, it stamped the new note for the new commit without checking the original, so a note copied from another commit or edited by hand came out `verified`. autter now checks the original notes first. A rewritten note derived from a failing one is still written, with its integrity stamp naming the source commit and its failure, and `autter verify` reports it as the new failure `carried_failure` (exit 5). `autter stats` and `autter blame` count its lines as unknown. A squash fails if any note folded into it fails. Untampered commits in the same rewrite still verify.
- **A note git copied unchanged during a rebase (`pending_rewrite`) must still have a valid digest.** A tampered note copied while the autter service was stopped used to pass with a warning; it now fails with `digest_mismatch`.
- Still not caught: a note edited with its digest recomputed (see `docs/scripting.md`), a commit a rebase adds at an `edit` stop without replaying an original, notes in `refs/notes/ai-stash`, and notes rebound by an earlier autter release.

## [3.8.0] - 2026-11-12

### Added

- **`autter verify`: an integrity check for authorship notes.** A note could be copied from another commit (`git notes --ref=ai copy -f <other> HEAD`) or edited by hand, and autter accepted it silently: an AI line could then be blamed to a person with no warning anywhere. Every note autter writes now records the commit it belongs to, that commit's tree, and the content id of each attributed file, plus a SHA-256 digest of the note. `autter verify [<rev|range>] [--json] [--strict]` checks them and reports each commit as `verified`, `legacy` (written before 3.8.0), `missing`, `pending_rewrite` (git copied the note during a rebase and autter has not rewritten it yet), `rebound_by_older_autter`, `unavailable` (objects missing, e.g. in a shallow clone), or one of the failures `wrong_commit`, `content_mismatch`, `range_out_of_bounds` and `digest_mismatch`. A failure exits 5 (`integrity_failed`); every other status exits 0, with a warning for the non-verified ones, also under `--strict` for now (a later release will make `--strict` fail on `legacy` and `missing`). Add `autter verify origin/main..HEAD --strict` to CI next to `autter ci` to catch a note that does not belong to its commit (see `docs/scripting.md`).
  - `autter stats` and `autter blame` skip a note that fails verification: its lines count as unknown, and one line on stderr points at `autter verify`.
  - Notes keep `schema_version` `authorship/3.0.0`; the new `integrity` member is ignored by earlier releases, so mixed teams keep working. Every rewrite autter performs (rebase including reorder, squash, fixup and renames, amend, cherry-pick, `cherry-pick -n`, reset, stash, and `autter ci` squash and rebase merges) writes a note that verifies for the new commit.
  - This is an integrity check, not tamper-proofing: someone who edits a note and recomputes its digest is not caught, because notes live in the repository's own Git data. A server-side record that makes later edits visible to the organisation is planned.
- **Kiro CLI support.** `autter install-hooks` installs Kiro CLI v3 hooks as one autter-owned file, `~/.kiro/hooks/autter.json`, which calls autter before and after every file write and shell command. It never writes hooks into a repository, and `uninstall` removes only that file. The hook prints nothing and always exits 0, so it can never block Kiro or add text to the agent's context. `autter doctor --agent kiro` checks the setup end to end. Kiro CLI 2.x is not supported. Kiro does not document which hook field carries the edited file's path, so autter reads every likely field; if a Kiro edit is not attributed, `docs/kiro-capture.md` explains how to capture a real hook payload and send it in. The Kiro IDE is covered only if it loads the same global hooks folder, which is not yet confirmed; the autter extension (Open VSX) records human edits there.

### Changed

- **CI runs tests on every pull request**: the lib tests and the core integration groups (attribution through rewrites, cherry-pick, rebase, install and `--help` safety), in addition to the build checks and the Windows jobs.

## [3.7.1] - 2026-11-12

### Added

- **`autter doctor --agent <name>`** checks one agent end to end: whether it is detected, which hook files autter manages for it, whether each hook command runs, and then a simulated pre- and post-edit hook call in a throwaway repository that must record an AI checkpoint. Names match by id, display name or alias (`claude`, `copilot`). `docs/agents.md` lists every agent, how it is integrated, what is and is not captured, and the command to verify it.
- **A setup reminder for npm installs.** npm hides install-script output, so a user who installed with npm never saw "run `autter onboard`". On an everyday command at a terminal, autter now says once a day that setup is not finished. Never in CI, from an agent hook, or with `--json` or `--help`.
- **A notice for agents installed after onboarding.** The next command names a newly detected agent once, with `autter install-hooks`. Nothing is installed without consent, and agents you left unselected in onboarding are never named.
- **CI runs the unit tests and an end-to-end check on Windows** for every pull request: service start, stop, restart and stale-lock takeover, an AI edit recorded and blamed through the trace2 pipe, `doctor --report`, VS Code with `Code.exe` ahead of `bin\code.cmd` on PATH, and the npm launcher's message for an `autter.exe` that will not start.

### Changed

- **npm installs keep the version npm installed.** The background service no longer self-updates a binary installed by npm; the update notice and `autter upgrade` give `npm install -g @autter/cli@latest` instead. Installing with `install.sh` or `install.ps1` over an npm install turns self-update back on.
- **Errors during setup say what to do next**: `bg start`, `bg restart` and `bg shutdown`, `upgrade`, `login --token`, `logout`, and per-agent errors from `install-hooks`, `uninstall-hooks` and `uninstall`.

### Fixed

- **Windows: one `install-hooks` could still open two VS Code windows** when only `Code.exe` was on PATH, because the VS Code and GitHub Copilot checks each asked it for its version. The answer is now remembered for the whole command, and the one manual extension-install step is shown.

## [3.7.0] - 2026-11-12

### Fixed

- **The background service could stay up while dropping every checkpoint** (since 3.3.0). When it could not start a handler thread it retried forever, its health check still passed, and `autter checkpoint` exited 0 with nothing recorded. The service now stops and restarts after 20 failures in a row or 5 seconds without serving a connection, its health check needs a reply on the control socket (not just a connection), and running out of file descriptors counts as unhealthy on the first check. Idle control connections are closed after 10 seconds and handler threads are capped at 512, so held-open connections can no longer pin it at its thread limit.
- **Checkpoints are confirmed.** The service now acknowledges each checkpoint as soon as it has read it, before processing it. A hook waits up to 200 ms for that receipt and says on stderr when a checkpoint may not have been recorded (it still exits 0); a direct `autter checkpoint` exits 1 without one. An older service without receipts is detected and handled as before. Hook checkpoints are also faster (median 35 ms to 9 ms in a debug build). Windows gets the same handler-thread cap and at-capacity restart as macOS and Linux.
- **Attribution kept through more rebases.** AI lines became the user's when a branch renamed a file and an agent edited it again before the rebase, across a chain of renames, when a new file was later created at the old path, when the rename was folded into the AI commit as a fixup, and when a later commit on the branch rewrote the AI line. A rebased note could also drop a line added above an earlier line by the same author. An interactive rebase that reorders, squashes or drops commits now pairs each rebased commit with the commit it replays (from the notes git copies, then patch IDs), instead of by position.
- **Attribution kept through `cherry-pick -n` and `reset`.** `git cherry-pick -n A B` (or two `-n` picks in a row) carried only the last pick's AI lines into the commit; a conflicted `-n` pick that was resolved and committed by hand lost all of them, including files that merged cleanly; a `git reset` that left HEAD where it was could be recorded as a move from the branch visited before, so staged AI work was committed as the user's. A conflicted pick is now worked out from the commits rather than the index, so staging a resolution early no longer credits hand-resolved lines to the AI; `checkout --theirs` keeps the AI's picked lines; a pick that is stashed and never popped or thrown away with `checkout -- .` or `restore` no longer attaches to a later commit; and a known-human checkpoint after a pick no longer claims picked lines it did not change. `git stash branch` keeps attribution, and `git reset --hard` drops the uncommitted AI attribution of the work it threw away, so text retyped by hand is not credited to the AI.
- **`autter show-prompt` picked the wrong commit among commits made in the same second** when an unrelated commit shared the timestamp, and spawned one git process per comparison (81 same-second commits took over 40 seconds; now about 2.5). The order is now history order, with the smaller commit id first among unrelated commits.
- **Usage metrics queue.** Another queue recovering reset the metrics queue's learned batch size and backoff, so it went back to sending the batch that was timing out. A clock stepping backward could schedule the next attempt far in the future, and the backoff was measured from the start of a slow request instead of from its failure. A partial "retry later" answer now halves the next batch. Rows the server rejects every time no longer block the queue: after repeated identical failures they are set aside (kept, not deleted), shown in `autter doctor` and `autter sync status`, and re-queued with the new `autter sync retry`.
- **`autter doctor` restarted a service that was only slow.** One missed probe was enough, which dropped work in flight on a busy machine. Doctor now keeps probing with a longer limit and restarts only a service that stays unresponsive, and says how long it waited.
- **Two hook refreshes could run at once** after an upgrade and rewrite the same agent config files; the refresh is now claimed under a lock.
- **`install.sh` did not sign in after a failed install-token exchange.** The install command copied from the Autter app carries a one-time token; when exchanging it failed the installer continued signed out without saying so. It now starts `autter login` before onboarding, or names the command when there is no terminal.
- **`autter log`, `autter blame` and `autter show` in a repository with no commits** printed git's raw error; they now say the repository has no commits yet, as `status` and `stats` do.
- **Diagnostics read the service's pid file from the wrong folder** when socket paths were shortened, so the service's start time and the outdated-binary check were never seen.
- **`AUTTER_TEST_FORCE_TTY` was read in release builds**; it is now test-only.
- **An install of the npm package from a checkout** fetched the 3.1.0 binary, because the checked-in package version was stale. It now resolves the latest release.

### Changed

- **`--strict` exit 3 means autter has no record.** `autter stats --strict` and `autter status --strict` used to exit 3 for any commit with no AI or known-human lines, so CI failed on ordinary hand-typed commits. Exit 3 now means capture missed the change: the commit has no authorship record (the service was down, hooks were missing, the agent is unsupported, or the commit predates setup). A hand-typed commit with capture working exits 0, and its `capture.status` is `captured`. A merge commit is judged on the lines that are in none of its parents.
- **`autter status` counts the whole working tree**, including files git does not track yet and hand edits; its totals now match `git diff`.
- **Range stats call lines from a commit with no record `unknown`**, as single-commit stats and blame do, instead of `untracked`. Range stats and `autter log` print the unsupported-agent note.
- **`--json` prints one document on every failure path**, including when the background service is unreachable (new error code `service_unreachable`), for an unknown command, and for `autter sync <unknown>`. `autter log` with a flag git rejects exits 2 (`usage_error`) instead of 1; an unknown revision in `log`, `diff` and `blame --ignore-rev` reports `revision_not_found`. `autter sync --json` runs `sync status`, and `autter <unknown> --json` with the service down prints one `usage_error` document.
- **`autter bg status` and doctor's service check need a reply**, so a service that accepts connections but does not answer is reported as unhealthy.
- **Windows start-up (not yet verified on a Windows machine):** longer waits for the service's first readiness and for the trace2 probe, a service that is up but has not processed an event yet is no longer reported as a failed start, a lock file left by a service that died is taken over, and a lock held by a service started from an Administrator window gets the elevated-service fix text.

### Added

- **`autter doctor --report <file>`** writes one support file: doctor results, measured timings, service and lock-file state, the last 200 lines of the service log, OS and git versions, and whether the process is elevated. Free text is redacted the way `autter debug` output is.
- **`install.ps1` dry run, progress and npm fallback.** `$env:AUTTER_INSTALL_DRY_RUN = '1'` prints what the Windows installer would do and changes nothing; the binary download shows progress at a terminal; a failed download names the URL and the npm route.
- **`autter blame --json` gives every line a category** (`line_categories`, `category_counts`), with the same names the other commands use, and session prompts' `accepted_lines` now match the commit's note.
- **`autter sync retry`** re-queues usage-metrics events that were set aside.
- **INSTALL.md says where autter is installed and why the location is fixed** (`~/.autter/bin`), and how to make `autter` available elsewhere.
- **CI:** a daily install smoke test that runs the documented install commands on macOS, Ubuntu and Windows, and a job that runs the npm launcher's tests.

## [3.6.0] - 2026-11-11

### Added

- **`install.sh --dry-run`**: `curl -fsSL https://api.autter.dev/install.sh | bash -s -- --dry-run` (or `AUTTER_INSTALL_DRY_RUN=1`) prints what the installer would download, write and start, and changes nothing. The installer also shows a progress bar for the binary download when run in a terminal, and names the npm route (`npm install -g @autter/cli && autter onboard`) when a download from GitHub fails. Unknown installer options are now an error (exit 2).
- **Onboarding ends with what it changed**: `autter onboard` closes with a list of what setup changed on this machine and the command that undoes it, and says that discarding the queued backlog is permanent.
- **`docs/background-service.md`**: what the background service does, what it listens to and how to debug it. `INSTALL.md` now says which install to use where (macOS, Linux, Windows, WSL, CI), and covers npm 10+ blocking install scripts, `npm update` not upgrading the CLI, and PowerShell's "not recognized" error.

### Changed

- **`autter doctor` names one root cause before setup**: on a machine where setup never ran, doctor prints a single "Root cause" line and "Next step: run `autter onboard`" instead of a list of dependent failures. In local mode the sign-in and upload checks are skipped instead of shown as warnings. A JetBrains IDE without the autter plugin is a warning, not a failure. A repository rooted at the home folder is a warning. Check time limits grow on machines where git itself is slow (`AUTTER_DOCTOR_TIMEOUT_SCALE` sets the scale by hand).
- **Superuser warning**: shown in full once a day and as one line otherwise, and not at all with `AUTTER_ALLOW_SUPERUSER=1`.
- **Background self-update holds in CI, for a pinned release and with `AUTTER_DISABLE_AUTO_UPDATES=1`**, so a pinned `@autter/cli` version is not replaced under a CI job.
- **CI compiles the Windows binary on every pull request.** Until now the first Windows compile was the release build, after the tag.

### Fixed

- **`curl … | sh` on Debian and Ubuntu**: the installer stopped with `set: Illegal option -o pipefail` because `sh` is dash there. Run as a file it now hands over to bash; piped to `sh` it says to run the same command with `bash` and changes nothing.
- **`autter uninstall` deleted the user's whole `[trace2]` git config section**; it now removes only the settings autter wrote.
- **`autter status` and `autter stats` in a repository with no commits** printed git's raw error; they now say the repository has no commits yet.
- **Credentials file errors name the file**, with what to do about it.
- **Windows: no more VS Code windows opened by `onboard`, `doctor` and `uninstall`** when `Code.exe` comes before `bin\code.cmd` on PATH. autter now runs the editor's command line (`bin\code.cmd`, or `cli.js` with `ELECTRON_RUN_AS_NODE`), treats an empty `--version` as an error and stops calling the editor for the rest of the command. A version doctor cannot read is reported as unknown instead of "predates native agent hooks".
- **Windows: an antivirus block or an elevated background service is named**: when Windows refuses to start the service (os error 225) or denies access to one started from an Administrator window, `autter bg start/restart` and `autter doctor` say so with the steps to fix it, instead of advising another restart.
- **npm on Windows: `spawnSync autter.exe UNKNOWN`** is followed by the likely causes (antivirus, incomplete download, wrong processor type) and the commands that check and fix each.

These Windows fixes are unit-tested and compile on Windows in CI, but have not been run on a Windows machine.

## [3.5.1] - 2026-11-11

### Fixed

- **A moved autter binary is caught for Claude Code, Droid, Gemini, Firebender and Windsurf**: these agents' hooks counted as up to date whenever an autter checkpoint command was present, whatever binary it named. When the binary moved (a nix store path, a dev build, a renamed home directory), the refresh after an upgrade skipped them and `autter doctor` reported "hooks installed (up to date)" while the agent ran a command that no longer existed and nothing was captured. The refresh now rewrites those commands, and `autter doctor` fails for the agent with the command that cannot run. The refresh still starts only when the CLI version changes; after moving the binary without upgrading, run `autter install-hooks`.
- **`autter --json uninstall-hooks` no longer starts a hook refresh**: the first command after an upgrade refreshes agent hooks in the background, except for commands that install or remove hooks themselves. That exception looked at the first argument only, so a global flag in front (`--json`, `--quiet`, `--no-color`, `--strict`, `-C <path>`) let a refresh run beside `install-hooks`, `uninstall-hooks`, `uninstall`, `upgrade` or `onboard` and rewrite the files they were changing.
- **A hook that names a command this autter does not have no longer blocks the agent**: after a downgrade, or once a command is renamed, an agent hook could run `autter <unknown> … --hook-input stdin`, which exited 2, the exit code Claude Code treats as "block the tool call". It now prints `{}`, says on stderr that the hook is out of date and how to refresh it, and exits 0, also when the background service is unreachable. An unknown command typed by a person still exits 2.

## [3.5.0] - 2026-11-11

### Added

- **Scriptable CLI for CI**: `--json` on every reporting command (`stats`, `status`, `log`, `show`, `blame`, `diff`, `whoami`, `doctor`, `sync status`), each document with `schema_version` and, on failure, an `error` object; documented exit codes (0 success, 1 runtime, 2 usage/outside a repo, 3 nothing captured, 4 capture broken); `--strict`/`AUTTER_STRICT=1` so `stats`/`status` fail when nothing was captured and `doctor` when capture is broken; no color, prompts or spinners when `CI` is set. ## [3.4.1] - 2026-11-09

### Fixed

- **Usage metrics no longer get stuck**: a metrics queue could stop draining for good because every retry sent the same 1,000-event batch and timed out the same way.   - Existing installations migrate automatically
  - Module retained only for migration purposes

### Technical Details

- **Architecture**: Three-component design with transcripts module, TranscriptWorker daemon task, and enhanced metrics schema
- **Processing Model**: 1-second polling interval for transcript modifications, priority queue for checkpoint notifications
- **Watermarking**: Per-agent configurable strategies handle diverse transcript formats (append-only JSONL, SQLite databases, etc.)
- **Migration Safety**: Automatic and idempotent, preserves all historical data

For detailed design rationale and implementation notes, see `docs/superpowers/specs/2026-04-29-telemetry-streams-design.md`.
